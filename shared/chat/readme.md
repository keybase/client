How chat works:

## Data ownership

Chat data is split across several focused stores instead of one global redux tree. Roughly:

- **Inbox metadata** (`chat/inbox/metadata.tsx`, `useInboxMetadataState`) is the single owner of conversation `meta` (trustedState, snippet, participants pointer, draft, timestamp, etc.) and `participants`. All meta writes go through `metasReceived`, which version-gates each incoming meta against the currently stored one (`Meta.updateMeta`) so a stale/out-of-order update can't clobber newer data. Callers that already merged from the current meta (e.g. `updateInboxConversationMeta`, error metas, incremental inbox sync) pass `{force: true}` to bypass gating. Converters live in `constants/chat/meta.tsx` (`baseMetaFromUIItem` is the shared base used by the various `*ToConversationMeta` functions).
- **Per-conversation thread store** (`chat/conversation/thread-store.tsx`) is a vanilla zustand store built by `makeThreadStore(conversationIDKey, uid, isLookingAtThread)` for one account, plain JS with no React. It returns the store, the thread's actions (store writes, mark read and its gating, the 500ms load throttle, retry, exploding mode, mark unread), the sticky username-header cache and `dispose`. It serves one account: the first time it finds that account not signed in it retires for good, and every action and every continuation of one (a late load, a mark unread waiting on the service) then does nothing. It holds `messageMap`/`messageOrdinals`/`messageIDToOrdinal`/`messageTypeMap`/`pendingOutboxToOrdinal`, the deletes this client has in flight (`pendingDeleteMap`, which is what shows a row deleting), live `typing` (a `Set<string>`), exploding mode, and payment/request/flip/unfurl maps. It reads conversation meta from the inbox metadata store rather than owning its own copy. Its service calls reach the adapter `setChatRpc()` installs, so a test swaps the service there and sets the real session and inbox stores. `chat/conversation/thread-context.tsx` is the React side: `ConversationThreadProvider` mounts one store per conversation and signed-in account (keyed on the uid, and nothing at all while no account is signed in, as between a switch's store reset and the next sign-in), gives it a check of whether the reader is looking at the thread right now (app active and focused, route focused), re-fires mark read whenever they are looking again (including when <Activity> shows the screen again) or when the conversation localizes, registers the thread's notification handlers and disposes the store on unmount; the hooks (`useConversationThreadActions`, `useConversationThreadSelector`, `useThreadMeta`, ...) read it. Thread search and the info panel are navigation, in `thread-navigation.tsx`. The rest is split: `thread-engine.tsx` holds engine-notification handlers (`applyMessagesUpdatedToThread`, `applyIncomingMutationToThread`, etc.) and `thread-load.tsx` holds thread-load logic (RPC calls, exploding-mode-from-gregor, pagination sizing).
- **Inbox rows are computed, not cached.** `chat/inbox/rows-state.tsx` exposes `useInboxRowSmall`/`useInboxRowBig`, which `useMemo` a display row from: inbox metadata (meta + participants), `chat/inbox/layout-state.tsx` (a memoized index built from the service's `UIInboxLayout`, used as a fallback for rows whose meta isn't trusted yet), `chat/inbox/badge-state.tsx` (badge/unread counts, fully replaced from each `BadgeState` RPC payload), and `chat/inbox/typing-state.tsx` (per-conversation typing username sets, merged in from `ChatTypingUpdate`). Merge precedence is one rule: meta wins whenever it's `trusted` or `error`; otherwise the layout row fills the gaps (snippet, draft, time, mute, name-split participants).
- **Message conversion** lives in `constants/chat/message.tsx` (`uiMessageToMessage` converts a single RPC `UIMessage` to the internal `Message` type; `parseUIMessagesJSON` does the same for a JSON-stringified array, used for bulk thread-load ingestion).
- **Orange line** (the "new messages" divider) is a small standalone store, `chat/conversation/orange-line-context.tsx` (`useExplicitOrangeLineState`), keyed by conversationIDKey -> `{ordinal, version}`.

## How data flows in

Engine notifications land in `shared/constants/init/shared.tsx`'s `_onEngineIncoming`, which hands every chat notification to `routeChatNotification` (`chat/notification-router.tsx`). The router decodes each notification type in one place (`stagesOf`) into what it does at each of three fixed stages, and runs them in order. First the inbox: calls (the multi-step ones in `chat/inbox/engine.tsx`) against the metadata store (`metasReceived`, `metaReceivedError`, `updateInboxConversationMeta`), the typing store (`updateInboxTyping`), an unbox request (`unboxRows`/`forceUnboxRowsForService`), the inbox layout, a desktop notification, the daemon's reacjis or the users store. Then the thread handlers, then the reload triggers, which mounted screens register per conversationIDKey in `chat/notification-registry.tsx`: the thread provider applies message updates, reactions, typing, attachments and payments through `useThreadNotifications` (`thread-engine.tsx`), as do the composer (`input-state.tsx`) and bot command status; the thread load status provider (stale threads) listens with `useReloadTriggers`. Meta readers (`useConversationMetadataReload`) and storeless message readers (`useConversationMessage`) listen with `useReloadTriggers` too. Registrations are keyed by conversationIDKey alone; a thread store whose account has left ignores whatever still reaches it. A notification about a conversation with nothing mounted stops after the inbox stage. Everything still reaches the engine listener bus (`engine/action-listener.tsx`) afterwards, for listeners outside a conversation (team retention, chat archive, manage-channels, maybe-mention).

Thread loads (initial, scrollback, centered, jump-to-recent) go through `loadMoreMessages` -> `loadConversationThreadMessages` in `thread-load.tsx`, which issues the RPC and calls back into the thread store's `applyThreadLoad`.

Every chat service call the conversation modules make (thread loads, mark read, posting, edits, deletes, reactions, attachments, conversation status, the exploding-mode gregor item, participants, pins, forwarding, unfurl previews, the info panel's settings and gallery, bots, typing and drafts, live location, delete history, the invitation-to-block dismissal, the rekey prompt) goes through one interface, `ChatThreadRpc` in `chat/conversation/chat-rpc.tsx`, looked up at call time through a thread's rpc or `getChatRpc()`. The service adapter there is the only code that builds the generated RPC params; tests install the in-memory adapter from `test/fake-chat-rpc.ts` instead of spying on generated functions. Chat RPCs outside a conversation stay direct: the inbox's own loading and layout (`chat/inbox/`), inbox and message search (`search-rpc.tsx`, `send-to-chat`), channel creation, blocking, and per-user settings (reacji skin tone, emoji lists).

What a user does to one message (delete, react, reply privately, collapse, remove an unfurl, pin, dismiss a journeycard) lives in `chat/conversation/message-commands.tsx`. Each command takes a target, and every target names its conversation: `{conversationIDKey, ordinal, thread}` for a row in a mounted thread, built by `useThreadMessageTarget(ordinal)` (`thread` is the provider's actions), where the command also updates the thread store (the deleting state, optimistic reactions, dropping the row), or `{conversationIDKey, message}` / `{conversationIDKey, messageID}` outside any thread, where only the service is told. The two `clientPrev` derivations, and which caller uses which, are in `chat/conversation/client-prev.tsx`.

## Lifecycle

The thread store (with its `ShownUsernameCacheContext` cache) is created by `makeThreadStore` when `ConversationThreadProvider` mounts and disposed when it unmounts. Disposing only drops a pending throttled load, because an `<Activity>` hide runs the same cleanup and the screen comes back on the same store; the screen mounts a fresh provider (via a React `key` on the conversationIDKey) when you switch conversations, so there's no manual "clear old thread" step — the old store and its listeners just go away. `ConversationThreadProvider` special-cases the case where the requested id matches the currently-provided one, reusing the existing store/actions instead of remounting (e.g. nested same-thread wrappers). On logout, `Z.resetAllStores()` (`util/zustand.tsx`) resets every store created via `Z.createZustand` — inbox metadata, badge, typing, layout, orange-line, etc. — back to its initial state; it's invoked from `stores/config.tsx` when `loggedIn` flips to false. It does not touch the notification registry (`chat/notification-registry.tsx`) or the engine listener bus (`engine/action-listener.tsx`): a screen still mounted across the reset (an account switch keeps logged-in screens up) keeps its registrations and subscriptions until it unmounts. The provider is keyed by the signed-in account, so it builds the screen's thread again for whichever account signs in next (and shows nothing while nobody is). Registrations are keyed by conversation id alone, which two accounts share for a team's channels, so until that rebuild renders the old screen can still hear the new account's copy of a channel. The thread built for the account that left has retired by then: its store's actions, and every late continuation of one, do nothing (`makeThreadStore`). Everything done for a thread asks the service through the thread's own rpc (`actions.rpc`, built by `makeThreadChatRpc` in `chat-rpc.tsx`): its screens (`useThreadRpc()`, or `thread.rpc` for a message command given one of its rows), its store and the load pipeline running for it. Once the thread retires that rpc asks nothing and never answers, so nothing after the await runs. `getChatRpc()` is for code outside a thread: the info panel, modals and storeless popups, the inbox, and the storeless message readers, which follow whichever account is signed in. The provider unmounts the old screen in the same commit its thread retires, so a click cannot reach a retired screen; only a continuation whose call was already in flight, or an unmount flush (the composer's draft save), checks `isRetired()` for itself. A screen's own handlers registered through `useConversationThreadNotifications` (the composer's command status and giphy, the bot-command status) hear nothing. Readers that load for whichever account is signed in (meta and storeless message readers) register with `useThreadNotifications`/`useReloadTriggers` directly and simply follow the current account.

## Intentional dualities

A few pieces of state are deliberately duplicated rather than unified, because they represent different things:

- **Typing**: the thread store's `typing` is a live `Set<string>` of who's typing right now in the open conversation; the inbox's `typingSnippet` (computed in `rows-state.tsx`) is a display string ("X is typing...") for inbox rows, sourced from the separate `typing-state.tsx` map so an unopened conversation's row can still show it.
- **Draft**: the composer's unsent text (`unsentText` in `chat/conversation/input-area/input-state.tsx`) is local, per-conversation UI state scoped to the input's own React context/reducer, cleared by unmount. `meta.draft` (in the inbox metadata store) is the last draft synced to the service, used to render the draft snippet on inbox rows for conversations you aren't currently looking at. They're independent by design — the input doesn't read from or write to `meta.draft` on every keystroke.

## Inbox

Conversations are of 2 basic types. - Small: adhoc conversations or teams with only the #general channel - Big: teams with multiple channels

We get a list of untrusted conversations from the server. Untrusted (unboxed) means we don't have any snippets and can't verify the participants / channel name. If we've previously loaded them the daemon can give us a trusted payload with the untrusted payload.
We request untrusted conversations to be unboxed (converted to trusted). This is driven by the inbox scrolling rows into view, via a queue (`queueMetaToRequest`) that unboxes in small batches rather than all at once.
The primary ID of a conversation is a ConversationIDKey. Data structures are mostly maps driven off of this key, split by store as described above (meta/participants, thread messages, badges, layout, typing).

The inbox operates in 2 modes: 'normal' and 'filtered'.
Filtered is driven by a filter string. Each item calculates a score and is sorted by this score (exact match > prefix match > substring match). We show small items, then big items. No dividers or hierarchy of channel/team.
The normal mode is split into 2 sections.

1. The small rows sorted by timestamp
1. The big teams alpha sorted (first by team, then by channel)

If you have a mix of small/big teams we can show a divider between them and truncate the small list.

Row display data is derived at render time from inbox metadata plus the layout/badge/typing stores (see above), not read out of a single cached map.

Edge cases:

- Rekey: If you don't have the keys to unbox the conversation we tell you who can help you out (sometimes yourself)
- Reset users: If you have reset users in an implied team conversation (no actual team in the teams tab) we present the reset users for you to deal with.

## Thread

A conversation thread is a list of messages. The thread itself is just a list of ids and each row is individually connected.
Messages have several IDs associated with them and they're used in different circumstances.

MessageID: is the true id of a sent message. This is used as input to rpcs (like editing/deleting)
OutboxID: is used when sending a message (while in the grey state)
Ordinal: is used to order / lookup messages. Ordinals are currently fractional additions to the last visible message id.
If i sent a message after the already sent {MessageID: 123} the oridinal would be 123.001
The ordinal is only used to ensure this client is seeing messages in order from their perspective. If you reload the thread those ordinals can be resolved into their real sent ids (aka 123.001 -> 124)
We keep the original ordinal if we can so the ordering of the thread from our perspective is static, even if the 'real' order is different. This means if you reload 123.001 -> 124 but during the session it will remain 123.001

## Pending

When we build a search for users we want to preview the conversation. We have a special conversationIDKey for this Constants.pendingConversationIDKey. This always exists in the inbox metadata store. The users go into the participants property. Usually the convesationIDKey inside the meta is the same as the key in the metadata store but in this special instance the key of the preview conversation goes in there depending on the participants
