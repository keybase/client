# Keybase E2E Flow Tests

## Overview

Two harnesses, one shared testID registry. Implement each flow on Electron and iOS together.

## Shared testID Registry

`shared/tests/e2e/shared/test-ids.ts` — single source of truth for all `testID` values.

**Adding a testID to a component:**
```tsx
import * as TestIDs from '@/tests/e2e/shared/test-ids'
// ...
<Kb.ScrollView testID={TestIDs.SETTINGS_ADVANCED}>
```

**Rule:** Add `testID` prop to an **already-existing** element (input, scroll view, pre-existing wrapper). Never add a new container just to attach a testID.

## Desktop — Playwright

| What | Where |
|------|-------|
| Test files | `shared/tests/e2e/electron/flows/*.test.ts` |
| Nav helpers | `shared/tests/e2e/electron/helpers/navigate.ts` |
| Run all | `yarn test:e2e:desktop` |
| Run branch | `yarn test:e2e:desktop:branch` |

**Navigation helpers:** `navigateToChat`, `navigateToFiles`, `navigateToTeams`, `navigateToGit`, `navigateToSettings`, `navigateToPeople`, `navigateToCrypto`, `navigateToDevices`

**Common pitfall — hidden nav stack elements:** React Navigation keeps prior screens mounted but hidden. `getByTestId(X)` may match 2+ elements (one hidden, one visible), causing Playwright strict-mode failures. Fix: use a selector unique to the destination screen rather than one shared with the source screen. Example: after navigating into a Files subfolder, the root screen's `files-browser` is still in the DOM but hidden — check for the Filter textbox instead, which only exists in subfolder views.

## Desktop release gate

The gate's code lives in `tests/e2e/shared/gate/` (shared with the iOS gate); its lists stay in `tests/e2e/electron/`.

`yarn test:e2e:desktop:release` (from `shared/`, about 45 min) runs everything and exits 1 on any failure, a flaky or skipped flow test included (retries stay at 1, so a flake shows as `flaky: <test>`).

- **Env:** accounts come from `~/.config/keybase-e2e/env` (mode 600, its dir 700; `yarn test:e2e:accounts:setup` fills in the peers); the environment wins over the file, and the run hands its children the account names (never paper keys). `KB_E2E_TEST_ACCOUNT_PREFIX` is the prefix every test account's name starts with: setup's repair of a block flow's leftovers writes only to accounts that have it, and refuses without it; `accounts:setup --check` reports it missing only when there is something to repair. Like every account name, it lives only in the env file. `KB_LEGACY_USER` (optional) names an older account signed in on the host's service and in the phone's app that holds what a new account cannot get (a Stellar wallet); it has no peer, a flow switches the app to it with `asLegacy(page, f)` only to read that state, and a flow that needs it fails naming the variable when it is unset. The main service must already be signed in as `KB_SMOKE_USER` (every flow test checks it again before it runs), and KBFS must answer `keybase fs ls /keybase/private/$KB_SMOKE_USER`; the FUSE mount itself is manual-only. The command never switches, stops or starts the main service or its components, and refuses with the command to run instead.
- **Peers:** the other accounts run in their own `keybase --home` services; the command starts them if they are down and leaves them running.
- **Phases:** preflight (release lock `/tmp/kb-e2e-release.lock`, one run at a time; account, ports 4000/9222, visual gate lock, an unlocked macOS session (a locked one refuses the window the native fullscreen the video flows need, so keep it unlocked for the whole run), KBFS, peers, `accounts:setup --check`) → launch the app → sweep leftovers once → `electron-flows` (light only) → relaunch with `--visual` and `visual:render` → census → report. It stops the app it launched at the end or on Ctrl-C.
- **Outputs** (`shared/tests/results/`): `electron-report.html` (flows, then tour entries, failures first), `census.md` (routes, windows and write RPCs no run reached; the windows besides the main one are listed by hand in `tests/e2e/electron/census-windows.ts` and credited by their `window/*` tour entries), `manual-checklist.md` (what to do by hand), `watchdog.log` (written only when the renderer went blank, which fails the run), plus one summary line per phase and a macOS notification.
- **Known failures:** `tests/e2e/electron/known-failures.ts` lists failures seen on master with their cause. They still fail the run; the report labels them "known on master", and says "now passes — remove it" when one passes.
- **Knobs:** `KB_E2E_RELEASE_ONLY=<grep>` runs only matching flows and the `settings/*` tour entries (to try the command; the census then reports gaps), `KB_E2E_RELEASE_TIMEOUT_MIN` (default 150), `KB_E2E_NO_OPEN=1`.

## Desktop flow rules

**Running while you change things:** run one test at a time with `yarn test:e2e:desktop:flows <file> --grep '<title>'`, once. Use `--repeat-each=N --retries=0` only on the ONE test whose flake fix you are proving. The full release runs at the end of a change, never between edits. A test stuck for more than about 5 minutes without clear progress gets reported with evidence, not dug into.

**Accounts and names:** every flow runs on the test accounts from `~/.config/keybase-e2e/env` (`loadE2EEnv()` / `loadE2EAccounts()`). Never put an account, team, password or paper key in the repo, a step name, an error or a log line. Team writes go only in `KB_E2E_TEAM` or a stamped subteam. Rows are found by exact name (`inboxRow(page, title)`, `openE2ETeam`, `openE2EChannel`), never "first row".

**Stamped names:** everything a flow creates carries the run id (`e2eRunId()`, `accounts/run-id.ts`), so the sweeper can find what a run left behind:
- channels, repos, emails, KBFS entries, devices: `stampedChannelName(label, runId)` → `e2e-<runid>-<label>`, label `[A-Za-z0-9_-]`. Emails are `e2e-<runid>-<label>@example.com`.
- message bodies and titles: `` `e2e-${e2eRunId()}-…` ``.
- teams: `stampedTeamName(label, runId)` → `e2e<runid><label>`, label `[a-z0-9_]` with no double underscore.
- emoji: `stampedEmojiName(label, runId)` → `e2e_<runid>_<label>`, label `[a-z0-9]`. An alias the service renames on a clash (a `#N` suffix) is no longer recognised as stamped, so pick labels unique within the run.
- a new kind of object needs a sweep rule in `accounts/sweep-lib.ts` too. `yarn test:e2e:accounts:sweep --dry-run` right after a run may list only that run's stamped chat messages (flows leave what they post for the next sweep, which deletes them by run stamp); anything else it lists, from that run or older, is a failure: every other object a flow makes it removes itself.

**Helpers** (`tests/e2e/electron/helpers/`, `tests/e2e/shared/`):
- `asSecond(page, f)` runs `f` with the app (and so the main service) switched to the second account through the account switcher, and switches back whether `f` passed or threw. `signedOutThenBack(page, f)` runs `f` on the login screen and signs smoke back in. `restoreToSmoke(page)` is the recovery both use. Any flow that switches accounts or signs out must end on smoke (`requireMainIsSmoke`).
- `dropFiles(page, target, paths)` drops real files onto an element; `pasteFiles` pastes an image (the main process's clipboard read is stubbed). Use `dropFiles` or Playwright's `filechooser` event for avatar and emoji pickers: they open a Chromium file chooser, not an Electron dialog.
- `connectMainProcess()` reaches the Electron main process through its Node inspector: `stubOpenDialog` / `stubSaveDialog`, `recordNotifications` / `takeNotifications`, `openUrl` (a `keybase://` link as the OS hands it), `recordExternalUrls` / `takeExternalUrls` (stubs `shell.openExternal`), `clipboardText`, `dropServiceSocket` (callers assert the count is above 0). Every stub in the main process, whoever left it, is restored after each test and before the inspector closes.
- `openRemoteWindow(context, main, name, props)` opens a remote window (menubar, tracker, pinentry, unlock-folders) and returns its page once its props have rendered; close it with `closeRemoteWindow`.
- `expectPersists(page, read, expected, what)` reloads the renderer, then `read` navigates back and reads the value. Use it for every "survives a reload" claim.
- `mainRpc(method, arg)` sends one RPC to the main service after checking it is on smoke; `mainRpcAsSecond` the same inside `asSecond`. They are for setup, read-backs and restores only.
- `CORPUS` / `TEXT_CORPUS` (`tests/e2e/fixtures/corpus/corpus.ts`) are the checked-in files and texts flows attach, drop and paste. Flows never send large data: an action that only runs while a transfer or job is in flight (cancel a download, delete an upload, pause a backup) is covered by a unit test of the real component, not by making the transfer slow. The one exception is iOS save-photos' cancel of a large image (about 43MB): the phone's menu opens in a bottom sheet the unit tests can't render, so that cancel is tested end to end.
- `openMenu(page, trigger, item, what)` opens every popup menu: the popup drops a show or hide within 100ms of its last one, so it waits that out, clicks once, fails if the menu does not open, and waits it out again before the pick. Any other show or hide right after one (an outside click to close) goes after `waitOutPopupDebounce(page)`.
- `retriedNavigation(what, attempt, opts)` is the only retry loop for getting somewhere (a list that redraws under the click, a search slow to find something new); it puts the try count on the test as a `retried` annotation. An asserted action is never retried: wait for its precondition (`waitSteady(locator, what)` for a row that must stop being replaced, `waitEnabledSteady(button, what)` for a button whose inputs reload) and press once.
- `step(...)` at every state change; `manualEdge(page, testInfo, id)` where a person takes over (the id is a `MANUAL_ONLY` entry in `manual-only.ts`).

**Coverage counts only from the app's UI.** Setup and read-back through the CLI, the peers or `mainRpc` are fine, but a census item is closed only when the app sends it. Every new write RPC in `protocol/bin/enabled-calls.json`, route or window needs a flow (or a tour entry, for routes and windows) or an entry in `census-exclusions.ts` with a real reason (`manual-only: <id>` names a `MANUAL_ONLY` entry). The census fails on an exclusion that is no longer needed, so remove it once a flow covers the item.

**Assertions:** check the outcome (the row, the setting after a reload, a CLI or peer read-back), never only "the modal opened". A flow that changes a setting reads it first and restores it in `finally`; a failed restore fails the test. No silent skips (`test.skip`, conditional early returns): missing setup fails and names what is missing. No blind retries, longer sleeps or soft-passes: retries stay at 1 and a flaky test counts as a failure, so find the cause.

**Known failures:** a deterministic app or service bug on master gets a strict test of the default user path that fails, plus an entry in `known-failures.ts` keyed `<file> › <describe…> › <title>` with its cause. The run still fails, and the report labels it "known" (check that it does: a key that does not match shows as a new failure). When the bug is fixed the report says "known now passes" and the entry is removed. A route-around for the rest of the coverage is a separate test, never a replacement. A strict failing test never goes in a serial describe: its failure and retry would rerun or taint the rest of the group.

**Secrets:** a password, paper key or provisioning phrase is typed only through `submitSecret` / `secret-input.ts`, which type through the main process and read back lengths only, so no Playwright action, assertion, trace or failure snapshot ever holds the value. A file that types a secret sets `test.describe.configure({retries: 0})` and `test.use({trace: 'off'})`. The secret-scan reporter (`secret-scan-reporter.ts`, and the release's secrets phase) scans every artifact for the env file's secrets, every second-account password the env file held during the run included (the start value, a `KB_SECOND_PASSWORD_NEXT`, the promoted one; kept in memory only), deletes any file that holds one and fails the run. `insertSecret` types only into a focused element matching its selector.

**The second account's password** is the harness's own: `KB_SECOND_PASSWORD` in the env file, a random value set by `yarn test:e2e:accounts:second-password`. Read it only with `requireSecondPassword`. A change goes through `rotateSecondPassword`: the new value is written as `KB_SECOND_PASSWORD_NEXT` first, then set, then `checkSecondSecretSurvives` (repaired once with `repairSecondSecret` on failure) and only then promoted. A leftover `KB_SECOND_PASSWORD_NEXT` stops every password flow until the owner checks which value the server holds; never edit the env file by hand. After a file signs second in through the app, or does anything as second that can drop its stored secret, its `afterAll` runs `checkOrRepairSecondSecret(env, requireSecondPassword(env), appRepairDeps(_electronPage))` and its `afterEach` runs `restoreToSmoke`. Such a file holds only those tests, so the rest of its area keeps traces and retries. The smoke account's password is never touched.

**Paper keys and devices:** a paper key a flow makes is recorded in the paper-key ledger (`accounts/paper-key-ledger.ts`: run id, device id and name, never the words) with `recordPaperKey`, and removed with `forgetPaperKey` once revoked; the sweeper revokes only ledger entries. A provisioned device is a new peer home `homes/prov-<runid>` with the file secret store, stopped with `ctl stop --shutdown` before it is revoked. Nothing provisions the main service.

## iOS gate harness

The iOS release gate's flows run through `shared/tests/e2e/ios-appium/gate.test.ts` (specs wired in `wdio.gate.conf.ts`); its helpers are in `tests/e2e/ios-appium/gate/`, and the gate core it shares with desktop in `tests/e2e/shared/gate/`.

- **Run:** `yarn test:e2e:ios:flows` (from `shared/`). Results go to `tests/results/ios-report/` (a Playwright-format json plus per-attempt records), project name `ios-flows`. `KB_E2E_RELEASE_ONLY=<grep>` runs only matching tests. Retries are 1; a flake is a failure, as on desktop.
- **`gate/step.ts`:** `step(name, opts)`, `manualEdge(id)` (a `MANUAL_ONLY` entry) and `retriedNavigation(what, attempt, opts)`, same contracts as desktop. A step on the inbox, or on a screen listing the account's other conversations or people (the inbox filter's results, the forward picker, the new-chat team builder), takes `{screenshot: false}` (its name only): those hold conversations and users that are not test ones. Failure screenshots stay in the local results, as on desktop.
- **`gate/errors.ts`:** console errors and uncaught errors (thrown, or an unhandled promise rejection) from the app, captured from a test's start (`beginErrorCapture` / `takeErrors`); an uncaught one fails the test. `appLogTail` adds the app log to a failure.
- **`gate/accounts.ts`:** `asSecond(f)`, `signedOutThenBack(f)`, `restoreToSmoke()`, `requireAppIsSmoke()`; every one ends on the smoke account.
- **`gate/secret-input.ts`:** `submitSecret(fieldTestID, secret)`, plus `focusSecretField`, `emptySecretField`, `fieldLength`; failures never carry the value.
- **`gate/device.ts`:** simulator helpers (`openLink`, `pushNotification`, `setLocation`/`clearLocation`, `setPasteboard`, `grantPrivacy`/`restorePrivacy`, `ensurePhotoCorpus`, `toBackground`/`toForeground`) and `relaunchApp()`, which terminates and launches the app and waits for its new JS runtime with error capture and the app-log capture running again. `launchedBy(deliver)` terminates the app and lets `deliver` (a link, a tapped banner) launch it, never launching it itself; a cold launch is then proved by the new runtime's first recording (`startRoutes`), since the app-log capture can't hold what it logged before it was installed. In a flow's `afterEach`, `launchIfGone()` (simctl and reads only) brings back an app a test left terminated; one that doesn't come back poisons the gate. `openLink`'s errors never hold the link. What changes the phone beyond the app runs only against `KB_IOS_UDID` (the release command sets it to the udid preflight proved booted) and names `keybase.ios`:
  - `grantPrivacy(service)` (`location`, `location-always`, `photos`, `photos-add`; never contacts) reads the original first (photos from the simulator's `TCC.db`, location from locationd's `clients.plist`), refuses one it can't put back, and returns the token a flow-level `afterEach` hands to `await restorePrivacy(token)` (simctl and reads only, once, read back over a few seconds; a failed restore poisons the gate). A photos or photos-add grant or reset kills the app; a location one doesn't: a photos restore that ran waits out that kill, so the `launchIfGone` after it brings the app back. The release refuses a phone whose location for keybase.ios was ever asked.
  - `ensurePhotoCorpus()` adds the corpus's photos and videos once per simulator data (recorded in `~/.config/keybase-e2e/ios-photo-corpus.json` with the simulator data directory's creation time, so an erase adds them again); nothing else may grow the library. Pick an item and prove it by read-back, never by grid position.
  - Save to Photos read-backs need full photo access, which no simctl grant gives (PhotoKit reads `simctl privacy grant photos` as undetermined, and a library query then reads empty): a flow takes `grantPrivacy('photos-add')` and `grantPrivacy('photos')` (their tokens put both back: iOS then holds Photos in place of PhotosAdd), then `system-ui.ts` `grantFullPhotoAccess()` has the app ask and taps the system prompt's Allow Full Access (credits nothing; the user-facing prompts stay manual-only). With it, a flow reads only the library's asset ids (`app-ask.ts` `libraryAssetIds`, `assetInfo`) and proves a save by the one id that was not there before (`gate/save-photos-lib.ts`; never the newest by date: a saved file keeps its own date, which can tie with the corpus's), then deletes exactly that id with `deleteSavedPhoto(id, before)` (refuses an id the library held before the test, taps iOS's Delete confirm once it has settled, reads it back gone). A deleted photo sits in the library's Recently Deleted for 30 days (the OS delete; the library a query reads does not hold it, so it is no per-run growth there). A photo a flow saved and could not delete poisons the gate.
  - `seedDocumentFolder(label, names)` makes a folder of this run (`e2e-<runid>-<label>-<hex>`) in the Files app's On My iPhone holding corpus files, for the document picker; the flow's afterEach removes it (`removeSeedFolder`, read back).
  - `pushNotification({convID, uid, body: e2eMarker('push-…')})`: it builds the one payload it sends, a `chat.newmessage`, never a silent type; the payload file is mode 600 under `/tmp/kb-e2e`, removed after.
- **`gate/app-log.ts`:** the app's logger lines, captured in its JS runtime (`appLogMark()`, `appLogSince(mark)`); never `start.log` or `metro.log`. A "didn't happen" read uses `appLogUntilMarker(mark, label)`, which logs a stamped marker through the app's logger and reads only the lines before it.
- **`gate/system-ui.ts`:** `findBanner(body)` (bounded: undefined after its deadline), `tapBanner(body)`, and `withNotificationCenter(fn)`, which opens it, runs `fn`, clears this run's notifications and closes it (a failure poisons the gate). The system pickers: `pickFromLibrary(names)` selects corpus items in the photo picker (its cells carry only a kind and a date and its search finds no file name, so the corpus is the one run of cells sharing a date in `gate/picker-lib.ts` `LIBRARY_GRID_ORDER`; cells are tapped at their frames, the selection read back before the confirm), `pickOnePhoto(name)` taps one corpus photo in the photos-only, single-pick picker an avatar or an emoji opens (it shows no videos, so the corpus is the run in `LIBRARY_PHOTO_ORDER`, and it hands the photo over on the tap, with no confirm), `pickDocument(folder, file)` opens On My iPhone > a seed folder in the document picker and opens the file, and a flow's afterEach runs `closeSystemPickers()` (escapeToTabs can't leave a document picker holding a selection; a failure poisons the gate). A pick is proven by what the app was handed: `pickedFiles(urls)` (a titles screen's paths) or `pickerCacheFile(cache, name)` (an upload keeps the copy's name) read the copy in the app's picker cache; a chat library pick is the corpus file byte for byte, a Files upload's library copy is re-encoded, so no hash ties it to the corpus: match it with `imageProps` by the format its bytes say and its pixel size together (the corpus png, jpg and heic are all 64x48, and the copy's file extension is only the picker's naming), a document pick is the file itself; an avatar's or emoji's pick is read off the screen with `helpers/profile.ts` `pickedImagesShown()` (the picker-cache images it draws: exactly one) and matched as a Files upload's. The flow credits `photo-picker` / `file-picker` after that read. Push permission is the owner's one-time grant: the release refuses without it, and no flow asks for it (asking opens the Settings app).
- **Device helpers:** `shared/devices.ts`'s `requireRevocableFromPhone(env, device, phoneDeviceID)` is the guard before any revoke from a phone flow: it refuses unless exactly one active device carries the expected name and it is not the host service's device, the env file's protected paper key or the phone's own device (an empty phone id is refused), and a flow's cleanup (`revokeLeftoverFromPhoneFlow`) goes through it too. `gate/accounts.ts`'s `phoneDeviceId()` (and `phoneDevice()` for the name) reads the phone's own device from the app over Metro, since the host's `keybase` CLI knows only the host's device. Pass it to the guard; never revoke by name alone.
- **Paper keys:** a flow that makes a paper key revokes it in the same test. While the words are on screen the flow takes no `step()` and no screenshot (nothing hides them there), the paper key is ledgered the moment the service lists it, and its cleanup revokes whatever the run made, relaunching the app if the paper key screen is still up. A paper key is read from the screen only to be revoked; no real paper key is ever submitted. A paper key's device name is the first two words of its phrase, so it goes into no error, step or log: the device helpers take it as `{name, label}` and say only the label, and replace the name with the label in any error from under them. That masking covers the errors wdio and Appium raise, not their logs: it relies on wdio's `logLevel: 'warn'` and on Appium running with no `logPath`, since a debug log records every selector, and a selector names the key. The app's dev RPC log redacts a paper key device's name, and every iOS run's secret scan (the flow run's, and the release's secrets phase) also looks for the names of the paper keys its own run made (`KB_E2E_SCAN_PAPER_KEY_NAMES`, `paper-key-names.json` next to the ledger, holding only the current run's names; the run's final scan deletes it, and the sweep deletes one a dead run left).
- **Provisioning by phrase:** the phone's code page offers only a camera scan, which the simulator lacks. A flow hands the computer's verification phrase to the app's own `submitProvisionTextCode` through `gate/secret-input.ts`'s `submitProvisionPhrase` (no Appium typing, never logged, held only in the wdio worker's memory, whose own scan at the end of the run looks for it in what the run wrote: `gate/run-secrets.ts`), and the scan itself is the manual-only `provision-qr-camera`. The phone's own code page shows a QR the whole time it is up, so no step runs then. Device names are never reusable, so a provisioning flow runs once per run id.
- **`gate/recorder.ts`, `gate/recording.ts`:** `PhoneRecording` records the simulator per attempt; `attemptRecording()` returns the running attempt's recording.
- **Harness RPCs are never credited.** Any eval that makes the app send an RPC itself (an `...RpcPromise`, a store action that sends one, `startAppAccountSwitch`, the configured-accounts ask, an outbox `CancelPost` cleanup, `askApp`) runs inside `withHarnessRpcs(what, f)` (`gate/recorder.ts`), which pauses the app's recorder and resumes it in `finally`. Wrap only the eval and its own wait: a UI tap inside the window goes uncredited. The recorder's `start()` clears any pause left open. `gate/harness-rpcs-lib.test.ts` scans `gate/` and `helpers/` and fails on an eval body outside `withHarnessRpcs` that is not a literal, a name or a builder on its read-only list.
- **Outgoing-RPC checks** read the recorder's call log through `gate/recorder.ts`: a mark from `currentCallSeq()` before, then `waitForUiCall(what, mark, method)` / `uiCallsSince(mark, method)` (the UI's calls: a call sent during a harness pause is left out), or `callsSince(mark)` for every call (each call's method and `paused`; the only param kept is `updateTyping`'s `typing`). A read throws when the app's JS runtime changed or its recording stopped inside the window (a relaunch or checkpoint), so an absence never reads an empty log; an absence check also waits for one positive call after its mark where it can. Never Metro's log or `.expo/dev/logs/start.log`.
- **"attempt over":** a test body is over once it settles or once mocha has moved on from it (a timeout). Every app command (wdio commands, `jsEval`, `simctl`, the gate's waits, `step()`) checks the attempt it is bound to (AsyncLocalStorage, `gate/attempt-binding-lib.ts`) and throws `attempt over: <title>` from an over body, so a timed-out body cannot drive the app while the afterEach or the next test runs. Hooks bind to no body and are never refused. Per-test timeouts stay the first line: each test's `this.timeout()` is at least the sum of its helper bounds plus its cleanup, with the sum in a comment.

**iOS differs from desktop:**
- The app's account is checked over Metro (`requireAppIsSmoke`): the app has its own service, so the host's `keybase` CLI says nothing about it.
- Secrets go in through Metro eval into the focused field's own `onChangeText`, never Appium typing, so no wdio command, log or screenshot holds the value. A file that types one sets `this.retries(0)` in its describe.
- `relaunchApp` keeps the recording going across the relaunch (a checkpoint before, one after), so a flow that relaunches still gets one recording.
- Flows are attributed to their own file: `gate/hooks.ts` wraps `describe`, so the aggregator `gate.test.ts` does not become every test's file. A test or hook outside a `describe` is refused as the file loads.
- **Flow hooks run outside the attempt.** A `before`/`beforeEach`/`afterEach`/`after` in a flow is not account-checked, the console errors it causes are cleared when the test starts, and `step()`, `relaunchApp()` and `attemptRecording()` throw there. Put app-driving setup in the test body. A hook that has to bring the app back to a known screen uses `escapeToTabs`, `goBackUntilGone` or a testID'd close (the inbox filter's `SEARCH_FILTER_CLEAR`), never a relaunch. A failing flow hook fails the tests it kept from running (or, for an `afterEach`, the test before it), citing the hook's error.
- **Restores that must not race go in a flow-level `afterEach`:** idempotent, bounded, with a read-back, its steps through `withCleanup` so one failed step does not skip the rest. Not a body `finally`: a timed-out body's `finally` is refused as "attempt over", and would race the next test anyway.
- **A crashed app is brought back by the root hooks** (`gate/crash.ts`): at each body's end and before its cleanup steps (inside the attempt), in the root `afterEach` and in the root `beforeEach`. A gone app is relaunched through the hang watch's relaunch and read back on the smoke account; the newest Keybase crash report since the app was last seen running is printed (`[ios gate] the app crashed; its crash report: <path>`) and the test it died in fails with "the app crashed (its crash report: <path>)". At a body's end an app gone with no report is left to the flow (it may have terminated it on purpose) and the root `afterEach` relaunches it; one gone between tests is a run error. A relaunch or read-back that fails poisons the gate (`poison-lib.ts`, as "the Keybase app"), so every later test is refused with what to put back by hand.
- A JS reload that no checkpoint saw (anything but `relaunchApp`/`grantPrivacy`/`attemptRecording().checkpoint()` after it) fails the test: the recording and errors from before it are lost.
- `yarn visual:render --ios <patterns>` renders the entries on the simulator and records the phone tour.
- **Render inspector-drop recovery:** the render driver's evals wait up to 15s for the app's inspector page and never run an eval twice. A capture whose first error is the lost inspector page is taken once more only when the app lived through the drop: the same pid in the simulator's `launchctl list` and the same JS runtime (the token the run last set, read back once the page is back). A process that died or a runtime that restarted keeps the entry failed, so a route that takes the app down is never hidden. A recaptured entry passes with a note on its own `✓` line, the release's render line counts it (`N recaptured after the inspector page dropped`), and its report card's label says `(recaptured)`.

## iOS release gate

Same core as the desktop gate (`tests/e2e/shared/gate/`); the iOS code is `tests/e2e/ios-appium/release.mts` (with `release-lib.ts`, `release-secrets.mts`, `launch.mts`, `census.mts` / `census-platform.mts`, `report.mts` / `report-platform.mts`).

`yarn test:e2e:ios:release` (from `shared/`) runs everything and exits 1 on any failure, a flaky or skipped flow test included.

- **Env:** same env file as desktop. The host service must be signed in as `KB_SMOKE_USER` (the sweep and setup run through it), and the app on the simulator must already be on the smoke account: the command refuses and says to switch with the app's account switcher. The `iPhoneTest` simulator (`KB_IOS_DEVICE`) must be booted and visible, with a signed dev build installed (detected through the `group.keybase` container in `simctl appinfo`). It never installs or uninstalls the app and never switches the host service.
- **Peers:** as on desktop; started if down and left running.
- **Phases:** preflight (release lock, same one as the desktop command; account; ports 8081/4723/8100; visual gate lock; unlocked macOS session; KBFS; peers; `accounts:setup --check`) → launch (its own Metro in watch mode, app relaunch onto that bundle, app-on-smoke check) → sweep leftovers once → flows (wdio gate, `ios-flows`) → render (`visual render --ios`) → census → report (each passes only on what its child wrote this run). However the run ends once it holds the release lock (a refused preflight, a failed phase, the deadline, Ctrl-C, a crash), it then stops only what it started (its Metro, the Appium its children left on 4723, and the WebDriverAgent that Appium left on this simulator); the simulator and app stay up. Then, even if stopping failed, the secrets scan (the env file's secrets, the run's paper key names and invite links, and saltpack armor of any message type) covers everything under `tests/results/` and the visual render root when `KB_VISUAL_RESULTS` moves it (a hit is deleted, named, and fails the run). The armor rule skips the desktop flows' files (`desktopFlowOutputs` in `shared/gate/secret-scan.ts`): the desktop scan does not treat armor as a secret, and a failed desktop crypto flow leaves its own test ciphertext there; a run refused at preflight scans only `ios-logs/`, as the rest may be another live run's files. Only then is the report opened, if it is still there. Preflight also stops a WebDriverAgent it finds on 8100 for this simulator once every other check passes: that is any earlier Appium session's on this simulator, the owner's own included, so finish your own Appium work on it first.
- **Outputs** (`shared/tests/results/`): `ios-report.html`, `ios-census.md` / `ios-census.json`, `ios-manual-checklist.md`, and the logs in `ios-logs/` (emptied when the run takes the lock).
- **Known failures:** `tests/e2e/ios-appium/gate/lists/known-failures.ts`, same contract as desktop (still fail the run; the report labels them). The crypto peer-decrypt entry can pass in a full run, because earlier chat flows send from the second peer and sync its keyring; that "known failure passed" is expected, and the entry stays until the Go fix lands (a run without those flows fails it again).
- **Lists** (`tests/e2e/ios-appium/gate/lists/`): `manual-only.ts` (what a person must do by hand; feeds the checklist), `census-exclusions.ts` (routes, write RPCs and surfaces the run need not reach, each with why; `manual-only: <id>` reasons name a manual-only entry), `surfaces.ts` (the native surfaces with no route). A flow credits a surface with `creditSurface(<surface>)` right after it asserts the app used it. The `gate/device.ts` and `gate/system-ui.ts` helpers (`openLink`, `pushNotification`, `setLocation`, `setPasteboard`, `relaunchApp`, `toBackground`/`toForeground`, `tapBanner`) only deliver and credit nothing (a jest source scan keeps `creditSurface(` out of `device.ts`): `background-foreground` is credited by the flow once it has asserted the round trip.
- **Knobs:** `KB_E2E_RELEASE_ONLY=<grep>` (only matching flows and the `settings/*` tour entries; the census then reports gaps), `KB_E2E_RELEASE_TIMEOUT_MIN` (default 275: the full run of the whole stack took 183 minutes), `KB_E2E_NO_OPEN=1`.

## iOS chat flows

The chat flows (`flows/chat-*.test.ts`) run in the gate like every other flow. Seeding is each file's describe-level `before(ensureChatData)` (20-minute bound on a first run).

- **The host stays smoke.** The host CLI and `mainRpc` act as the smoke account and are never switched. Incoming messages, typing, attachments and "second leaves" come from the second account's peer (`peerSender(loadE2EEnv())`, `sendWithRetry`, `IncomingSender.leave` / `attach`); a host CLI send is smoke's own message from another device, used only where that is the intent. The second account's own state is read through `ensurePeer('second').rpc()`.
- **`requireSecondNotBlocked()`** runs in the `before()` of every file that needs the second account (messages from it, `asSecond`), in chat and in later PRs' files: a chat-blocks restore that failed refuses there instead of running blind. `chat-blocks` registers last among the chat files in `gate.test.ts`.
- **Inbox rows:** the native inbox is a LegendList that draws only near rows. `scrollInboxTo(name)` finds a row by its exact name (a channel as `#channel`, only under `KB_E2E_TEAM`'s header), refuses a name more than one drawn row matches, and never names a row in its errors; `openFromInbox(name)` taps it. The inbox's end is two drags in a row that change nothing. An absence (`inboxHasRow` false) follows a row the test expects there, and is paired with the app's own layout read (`appInboxLists(convID)`). A flow that claims "open from the inbox" taps the row, never `keybase://convid`. Never pick or name other rows: the inbox holds conversations with the personal account.
- **A control with no element of its own** (rulings in the PR 5 ledger), two cases:
  - *It has a native view* (a `Kb.Button` inside a row whose tappable box merges it into one element, such as Browse all channels' Join): `tapControlIn(rowElement, {prop, value}, label)` finds exactly one button labelled exactly `label` under the one component whose prop matches, measures its view and the row component's view (`measureInWindow` is in the app's window, which for a modal sheet is not the screen), places them by the row element's on-screen frame, and taps the middle of the button only when it lies wholly inside the row element and on screen.
  - *It has no frame* (inline pressable text inside a message's text, such as a failed send's "Edit or Cancel", which Fabric draws as virtual text inside its paragraph): `pressInlineText(ordinal, text)` calls the handler a tap fires, found under that message only (exactly one text rendering exactly `text`), outside `withHarnessRpcs` since it is the app's own UI handler; the flow adds a `manualEdge` so a person checks the physical tap.
  A control with no label (the profile's avatar, merged into its avatar-and-name element `PROFILE_AVATAR_NAME`) is named as `{handlerOf: 'onEditIcon'}`: the one component whose onClick is the scope's own prop of that name.
  Either way, read back the effect, not the call alone.
- **A modal's switches** (Kb.Switch, e.g. the block modal's): XCUITest's frames for them are not where they are drawn, so taps there do nothing. `tapSwitchLabelled(label, anchorElement, anchorLabel)` measures the switch's own view, places it on screen by a button of the same modal whose element is on screen (`measureInWindow` is in the modal's window), taps it, and waits for it to turn. Before ruling that a control takes no tap, tap its own measured frame.
- **A pressable text whose element is wider than its word** (an attachment's "Collapsed" label is reported with its line's full width while the word sits at the left, so a tap on the element's middle lands beside it and does nothing): `tapTextIn(element, ordinal, text)` finds exactly one pressable text rendering exactly `text` under that message, measures its own view, and taps that frame's middle only when it lies wholly inside the element and on screen.
- **Search filters** (`SearchFilter`: the inbox filter, the forward, channel, member and bot pickers) are one accessible box (`SEARCH_FILTER`), so the text field inside is not in the tree: `typeInSearchFilter(text)` focuses the box and types with paired key actions (`typeIntoFocused`). WDA refuses `browser.keys` with more than one key (an unpaired keyDown). An element `addValue` taps the field's middle first, which moves a multi-line composer's cursor: to type on where the app left the cursor, use `typeIntoFocused`.
- **Labels with an icon** carry the icon font's glyph (Unicode private use) and ", " before the text: a menu item reads "<glyph>, Edit", a danger-zone button "<glyph>, Block", a pinned inbox row "<glyph>, <name>, …". Match by `ENDSWITH ", <text>"` (`iconButton`, and the sheet items `chooseMenuItem` and `menuHas` read), never `BEGINSWITH ", "`.
- **Many-element reads go through one page source** (`gate/page-source-lib.ts`): a WebDriver call per element and attribute costs ~65ms. Leave out `visible` (`mobile: source` with `excludedAttributes`) where the reader does not need it: it is most of a source's cost on a long list.
- **The simulator's pasteboard** takes no writes from outside on this host (`simctl pbcopy`, WDA's `mobile: setPasteboard` both leave it empty): `setPasteboard` writes through the app's own clipboard module and reads it back.
- **`expectPersists(what, read, want)`** relaunches the app (`relaunchApp`, recording checkpointed), waits for it to sign in (`waitSignedIn`), and reads the value back where it shows. Pick a non-default `want`, or it proves nothing.
- **What a chat flow puts back** (flow afterEach, read back): conversation status (hide, mute, block), pinned conversations and pinned messages, notification settings, min writer role, unfurl settings, blocks plus the smoke and second folder favorite (`shared/favorites.ts`, then `accounts:setup --check`), installed bots, exploding mode, skin tone; throwaway channels and subteams are deleted by the host. The sweeper catches stamped messages, channels and subteams only.

The `--check` (and desktop's rotation) switches the host's main service to the second account and back; a switch that gives no answer gets one switch back and then the owner action.

## iOS native surfaces

The app-level and native flows (`app-deep-links`, `app-push`, `app-lifecycle`, `chat-location`, `chat-attachments-picker`, `files-upload`, `files-save-photos`, `profile-avatar`, `teams-avatar-emoji`, `share-extension`) reach outside the app through `gate/device.ts` (`simctl`, attempt-checked, udid from preflight) and `gate/system-ui.ts` (springboard, Notification Center, the photo and document pickers, system alerts). Neither credits anything: a flow calls `creditSurface(...)` once it has asserted the app used the surface.

- **Privacy:** `grantPrivacy(service)` reads the original from the simulator's `TCC.db` (location from `locationd`'s clients plist), grants with the bundle id `keybase.ios` (never `all`, never a reset without the bundle id) and returns a restore token; `restorePrivacy(token)` in the flow's `afterEach` puts it back exactly and reads it back. Every photos grant or reset terminates the app within a second; location ones do not.
- **simctl's photos grant is invisible to PhotoKit:** the app reads full access as undetermined after `simctl privacy grant photos`. Full access comes only through the app's own prompt, accepting "Allow Full Access" (`grantFullPhotoAccess`). The pickers need no grant at all (PHPicker runs out of process).
- **Photo corpus once per simulator:** `ensurePhotoCorpus()` adds the committed corpus (`fixtures/corpus/`) once and records the udid and sha256 list in `~/.config/keybase-e2e/`; it is never added per run. A flow picks corpus items by name and proves the pick by read-back (sha256, or format and pixel size where the picker re-encodes), never by grid position.
- **Save to Photos deletes only recorded saved ids:** the test reads the whole library first, records the one new asset id the save made, and its `afterEach` deletes exactly the recorded ids. Deleted assets sit in Photos' Recently Deleted for 30 days; nothing else in the library is ever touched.
- **Push:** `pushNotification` delivers through `simctl push` (payload file 0600 under `/tmp/kb-e2e/`, never a silent payload). Push permission is granted once on the simulator by the owner (simctl privacy has no notification service); preflight refuses without it. No flow calls the app's `requestPermissions`.
- **App log capture, not log files:** `gate/app-log.ts` captures the app's logger lines inside the JS runtime after each launch (`appLogMark` / `appLogSince` / `appLogMarker`); flows read it and the recorder, never `start.log` or `metro.log`. Cold-launch checks read `startRoutes` / `appSnapshot`.
- **The share extension** runs in its own process: its log (`extensionLogSince`) and the group container's manifest are its read-backs, and every share ends with a host CLI read-back of the sent message in smoke's self conversation.
- **A context menu is held once on a frame read twice:** the hold's target frame is read until two reads half a second apart agree, then held once; there is no second hold, since one made while a menu is up lands on that menu.
- **No gate wait outlives Appium's newCommandTimeout silently:** a wait that sends no WebDriver command pings the session (`gate/hang-lib.ts`) or refuses; a 300 s silent wait once ended the session and the rest of the run.
- **The release refuses a pending outbox:** launch reads the app's outbox and refuses while any entry is pending (a failed post retries for a long time and holds the app background-active). A flow that can leave one (chat-location's map posts) cancels its own in `afterEach` and reads the cancel back.
- **The poisoned flag:** a restore whose failure leaves the phone broken (a privacy or location restore, Notification Center left open, a stuck share manifest, a seed folder left, the app not relaunchable) calls `poisonGate(what, byHand)` (a flow wraps such a restore in `gate/poison-lib.ts` `guarded(what, byHand, restore)`, which also clears the poison once it lands, and which poisons nothing for an attempt that is over, as a retry restores the same setting). A cleanup of something an attempt made (a seed folder, through `removeSeedFolder`, a saved photo, the pasteboard's image) passes `guarded` a `leftover` check as well: when it does not finish, cut off or not, it poisons only if the thing is still there or the check cannot read it. Every later test fails at once naming it, and the release fails. A person clears the phone by hand.
- **Inline pressable Text:** iOS draws inline pressable text (`RCTVirtualText`) with no accessibility element or frame; the flow calls that control's own `onPress` over Metro (exact text, in its row, exactly one) and adds a `manualEdge` for the physical tap. Never a coordinate guess.
- **State-carrying testIDs:** where iOS shows no control state (a checkbox, a radio, a toggle-like row), the testID carries it (`<ID>:on` / `<ID>:off`), registered in `shared/test-ids.ts`; reads go through the testID.
- **Never pressed:** the camera's "Take photo or video", the composer's audio record button, "Import phone contacts", "Share to another app" (the system sheet out), Photos' Delete on anything but the test's exact saved asset, `pbsync` (the host's clipboard), and anything that cuts the network (offline and reconnect are manual-only). The account and settings never-press list above still holds.

## iOS — Appium + WebdriverIO (TypeScript)

| Command (from `shared/`) | What it runs |
|------|-------|
| `yarn test:e2e:ios:release` | the whole iOS release gate (preflight, launch, sweep, flows, render, census, report, secrets) |
| `yarn test:e2e:ios:flows` | the gate flows alone (`wdio.gate.conf.ts`, spec `gate.test.ts`, one session) |
| `yarn test:e2e:ios:census` | the census again over the last run's results |
| `yarn test:e2e:ios:gate-report` | the report again over the last run's results |
| `yarn test:e2e:accounts:second-password --check` | after a release: the host's stored secret for the second account |

Flow files are `shared/tests/e2e/ios-appium/flows/*.test.ts`, the gate's helpers `ios-appium/gate/`, the element and navigation helpers `ios-appium/helpers/`.

Drives the **already-installed** app black-box (no rebuild). Selectors: `~<testID>` (testID → iOS accessibilityIdentifier). Helpers: `el/els/waitForTestID/byText/tab` (elements), `escapeToTabs/goBack/navigateTo*/scrollDownToText` (navigate). `escapeToTabs` runs before every test (resets to the tab root).

**Gotchas (hard-won — read before adding flows):**
- **Native tab bar:** tap tabs by **label** (`tab('People')` → `~People`), NOT `nav-tab-*` testIDs — those don't reach the native `UITabBar`.
- **Container testIDs** (a flex `Kb.Box2` wrapping a list) report `visible="false"` to XCUITest even when on screen → use `waitForTestID` (it uses `waitForExist`, presence), never `toBeDisplayed`.
- **testIDs must be on the MOBILE-rendered element.** Many components branch on `isMobile`/`.desktop`/`.native`; a desktop-only testID is invisible on iOS, so a flow that waits on it passes on desktop while testing nothing on iOS. Put the testID on the **clickable/leaf** element (e.g. `Kb.ListItem`'s `testID`, a `ClickableBox`), not a non-clickable wrapping `Box2` — wdio `.click()` no-ops on a non-accessible container.
- **`byText` uses CONTAINS** — tappable rows have merged accessibility labels (e.g. `", Crypto"`), so exact match fails.
- **`Kb.Tabs`** supports a per-tab `testID` (needed for icon-only tabs like the team Settings gear). The app remembers the last-selected team tab → select tabs by testID, don't assume the default.
- **Modals:** dismiss via Done/Close/Cancel (`escapeToTabs` does this first, before back buttons — a modal's back button is a no-op that loops).
- **HMR applies testID/component changes** to the running sim app — no manual reload needed when adding testIDs.
- Wait for a **real data row** (not just the list container) before asserting/screenshotting, so shots show loaded content.

**iOS tab structure:** People & Teams are direct tabs; Chat & Files have their own nav helpers; Crypto/Devices/Git/Settings live under the **More** tab (`navigateToMore`).
