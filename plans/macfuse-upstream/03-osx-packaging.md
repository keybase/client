# 03 — osx native + packaging

Status: [ ] not started

## Goal

Stop building, bundling, installing and loading kbfuse from `osx/` and `packaging/` (D1, D12). New installs get no privileged helper and no redirector (D25), and no installer path can bless the helper any more: the app-bundle path goes too (D38). `KeybaseInstaller` gains one switch, `--retire-helper`, that runs the D29 migration (plus the D40/D41 directory cleanup) against the already-installed helper 1.0.47 without blessing a new one. The native side reports **no** macFUSE status; `keybase fuse status` (02) is the only source of truth. Merging waits on a signed, notarized `KeybaseInstaller` 1.1.95 (D33).

## Depends on

- `decisions.md`: D1, D9, D12, D14, D25, D28–D30, D33, D38, D40–D42.
- **02-install-status-cli** stops exec'ing every installer switch this layer deletes (`--install/uninstall-fuse`, `-redirector`, `-helper`, `-cli`) and `--install-app-bundle`/`--uninstall-app` (D38), and calls `--retire-helper` instead, treating any non-zero exit as "retry next launch" (D29, D33).
- **01-mounter** settles the D30 mount point (spike). It decides whether `--install-mountdir`/`--uninstall-mountdir` survive (only for the `~/Keybase` fallback's Finder sidebar entry). 01 also carries the darwin redirector packaging edits, because its build-tag change would otherwise break the darwin prerelease build.
- **04-ui** drops the consumers of exit codes 4, 6, 8 and 300 and keeps 5, which 02 generates (D31). After D38 the installer itself exits only 0 or 1.

## Risks / open questions

- **Decided:** the app-bundle path, `KBHelperTool`'s install path, exit codes 6/8 and error -303 go now (D38). `/Volumes/Keybase` is stopped and removed by the retire run (D40). Under the `~/Keybase` outcome the old `/Volumes/Keybase (<user>)` is removed too (D41). `osx/Helper/` is deleted and unbundled one or two releases after ship, tracked in the README (D42).
- **Owner decision (new, from D41):** the retire run removes the helper, so it runs once per machine, as whichever macOS user launches first. D41 as written removes that user's `/Volumes/Keybase (<user>)` only; other accounts' dirs would then stay forever, since nothing with root is left. Widen step 4 to every `/Volumes/<appName> (*)` directory that is not a mount point (the guard still applies; step 2 already failed if any kbfuse mount was live)? The spec assumes the narrow D41 reading until answered.
- **Owner question (new, from D38 + D42):** after D38 nothing blesses the helper copy bundled in the installer, so it is dead weight from this release on. D42 keeps bundling it for one or two more releases. Is there a reason to keep shipping it that long (the `--retire-helper` run does not need it), or can the Copy Files phase go now while the `osx/Helper/` source waits for D42?
- **Risk:** `stopRedirector` only kills the redirector task that the *current* helper process launched (`KBHelper.m:361-364`). If the helper restarted since, a redirector may still be running; the change 6 guard then fails the run instead of deleting into it, and it retries every launch until a reboot. **UNVERIFIED** how often that happens.
- **Risk, UNVERIFIED:** helpers older than 1.0.47 may lack a method the retire run calls; that user then retries every launch (02 Risks proposes a cap).
- **Risk, UNVERIFIED:** whether `kmutil unload` plus deleting `kbfuse.fs` fully removes the kext from the auxiliary kext collection on Apple Silicon, or it lingers until reboot. The stale approval entry in System Settings likely remains (cosmetic).
- **Risk, UNVERIFIED:** removing the launchd plist of a loaded job leaves the job registered until reboot. If the helper exits early, launchd cannot relaunch it (binary gone); harmless, because nothing calls it after the run.
- **Risk:** GBCli rejecting an unknown switch (rather than ignoring it) is **UNVERIFIED**. If 1.1.94 ignores `--retire-helper`, it runs a no-op install and exits 0; 02 would then wrongly treat the retirement as done. 02 must re-check that the helper binary is gone after a 0 exit and treat its presence as a failure.
- `package_darwin.sh:234` re-signs Keybase.app with `--deep --force` (pre-existing, covered by dmg notarization).
- `KeybaseStatus` is not packaged; trimming its control panel is assumed fine.
